### 3.8 为什么 600 点里 98 点超标、却只报 1 次警（源码实证）

来源：`body\engine.py` 第 2545 行 `_alerts()` 内：

```python
fire("hyper", s.glucose > 11.0, "warn", f"高血糖 {s.glucose:.1f} mmol/L")
```

而 `fire()` 的实现（同文件 `_alerts()` 开头）：

```python
def fire(key, cond, sev, text):
    if cond and not self._last_alert.get(key):
        self._last_alert[key] = True
        self.bus.emit(Event(s.t, "alert", sev, text, {}))
    elif not cond:
        self._last_alert[key] = False
```

**两条硬结论（源码可验证）**：

1. **告警阈值是 `glucose > 11.0`，不是 7.8。** 7.8 只是常见的餐后参考线，插件并不据此报警。所以 98 个 >7.8 的采样点**本来就不会**触发任何告警——不是漏报，是设计如此。
2. **告警是边沿触发（只在跨阈值瞬间发一次）**，靠 `_last_alert` 字典去重。血糖长期停在 11.0 以上只要没跌回来过，就**永远只会有那一次告警**。这意味着「告警次数」不能作为「高血糖严重程度」的指标。

> **推测（非实测）**：第 6 天的 11.0 告警说明当时确实短暂越过了 11.0。但 `samples` 环形缓冲只保留了第 8 天，**无法回溯核实第 6 天的实际峰值**。这是数据可得性的硬限制，不是没查到。

### 4.5 「质量恒为 0」——**不成立，已证伪**

`state.sleep_quality = 29.74842767295598`，是明确的非零值。

再用源码把 29.75 逐项复算（来源 `engine.py` 第 867~893 行 `_settle_sleep()`）：

```python
total   = s.dur_light + s.dur_deep + s.dur_rem     # = 1480 + 640 + 0 = 2120 s
total_h = total / H2S                              # = 0.5889 h  ← 与 state.last_sleep_hours 一致 ✅
deep_r  = s.dur_deep / total                       # = 640/2120 = 0.30189
rem_r   = s.dur_rem  / total                       # = 0/2120   = 0.0
awake_h = s.dur_awake / H2S                        # = 0.0

dur_score  = max(0, 40*(0.5889-4.0)/2.0)                      = 0.0     # <4h 直接 0 分
deep_score = 30*max(0, 1-|0.30189-0.225|/0.225)               = 19.748  # 20~25% 为满分区间
rem_score  = 20*max(0, 1-|0.0-0.225|/0.225)                   = 0.0     # REM 为 0 → 0 分
cont_score = 10*max(0, 1-0.0*2.0)                             = 10.0

sleep_quality = clamp(0 + 19.748 + 0 + 10) = 29.748  ✅ 与存档 29.74842767295598 完全吻合
```

> **结论：睡眠质量公式工作正常，不是坏了。** 29.75 之所以低，是因为**最近一次睡眠是 13:18 那个 0.65 小时的午睡**（`last_sleep_hours=0.5889`，且 REM=0），被按「一整晚」的尺子打了分。这是**小睡污染了质量指标**的语义问题，不是计算 bug。

### 4.6 睡眠负债 13.12 小时——**数值真实，但单位口径需注意**

源码（`engine.py` 第 914 行）：

```python
need = max(4.0, float(getattr(self, "sleep_need_hours", 7.5)))   # 默认 7.5h
shortfall = max(0.0, need - total_h)
if shortfall > 0.0:
    s.sleep_debt = clamp(s.sleep_debt + shortfall, 0.0, 48.0)
```

同文件第 921 行还债：`s.sleep_debt -= max(0, effective_h - 1.0) * 0.9`（只有 `total_h >= 3.0` 才还）。

**手工复算**（按 17 个时段的事件时长）：

| 类型 | 累计 |
|---|---|
| 主睡（≥3h）合计 | 4.29+5.95+6.95+7.46+7.01+9.50+9.49+6.97 = **57.62 h** |
| 短睡（<3h，共 9 次）合计 | 1.30+0.42+0.57+0.57+0.57+0.42+0.42+0.23+0.65 = **5.15 h** |
| 全部睡眠 | 62.77 h |
| 按 8 晚 × 7.5h 计的需求 | 60.0 h |

> **推测（本单元推断，非直接读到）**：13.12 h 的负债无法用「8 晚时长不足」解释——48 小时清醒本身就会按 `s.sleep_debt += dt / H2S`（第 287、417 行）持续累积。也就是说 `sleep_debt` **在清醒期间也线性增长**，它是一个「清醒越久越欠」的积分量，而不只是「睡不够的缺口」。这解释了 13.12 这个偏大的值。
> **未能验证的部分**：由于 `samples` 只保留 10 小时、存档不记录历史 `sleep_debt` 曲线，**无法逐点复现 13.12 的累加过程**。此条标注为推断。
