## 一、这一版解决了什么

用户原话：**「不管中途有没有突然醒过来，只要是一整夜，那就得算在一块。」**

旧实现里根本没有「夜」这一级 —— 只有「连续睡眠区间（bout）」，而夜数直接拿
`len(bouts)` 统计。结果：夜里醒来一次就被数成两夜，服务器实测 7 天报出 **11 夜**。

### 新增的「夜」这一层

| 概念 | 判定 | 例子 |
|---|---|---|
| bout | 连续睡眠区间，容忍 0.5h 间隙 | 23:10 → 02:00 |
| **夜** | 同一 `night_key` 内的所有 bout 合并 | 23:10→02:00 + 03:00→07:20 = **一夜** |
| 午睡 | 落在日间且短于 4h | 13:20 → 14:29 |

**分界取正午 12:00**（`NIGHT_CUTOFF_HOUR`），不是午夜 0 点 ——
午夜分界会把 23:00–07:00 的整夜劈成两夜。凌晨 3 点入睡因此仍归属前半夜那一晚。

## 三、顺带修掉的三个真 bug（都很隐蔽）

1. **午睡结算不清账本** —— `is_nap` 分支只清 `sleep_bout_start_t` 就 `return`，
   四个 bout 时长账本留着。而 `_sleep_view()` 优先读 bout 账本，于是面板一直显示午睡时长。
   服务器实测：`start_t=0` 但 `light_sec=1390`、`deep_sec=760`。

2. **`_wake_up()` 不记 bout 结束时刻**（最严重）—— 唤醒只置 `wake_pending`，
   没写 `sleep_bout_end_t`。于是 `_flush_sleep_bout` 里 `if last <= 0: return` 直接跳过，
   这段 bout 永不结算；重新入睡时判否 `same_bout`，账本清零 ——
   **已经睡过的几个小时整段丢失**。
   实测：23:00 睡 3h → 叫醒 1.5h → 再睡，修复前只剩 3.22h，前 3.22h 消失；
   修复后 2.61h + 3.22h = 1 夜 5.83h。

3. **周期序号每次入睡归零** —— `stage_index` 无条件清零，「第 N 周期」永远显示第 1 个。
   现在只在换夜时归零；并用 `sleep_bout_cycle_base` 记基线，避免夜间合并时周期重复计入。

## 六、2026-11-27 追补：午睡仍在冒充「这一觉」的睡眠结构

用户报障：**「睡眠时长记录把午睡算进去了」**，且看起来像是时好时坏。

### 根因

第三节的 bug 1 只修了一半。午睡分支清的是 **bout 账本**（`sleep_bout_*_sec`），
而 `_sleep_view()` 在账本为 0 时回落的是 `dur_light / dur_deep / dur_rem` ——
这三个累计量**只在「新一段 bout 入睡」时清零**（engine.py 入睡分支），
午睡分支从不碰它。

服务器存档实测（d18，13:38–14:49 那场午睡）：

```
dur_light = 1560 s → 0.43 h     面板显示 0.4h
dur_deep  =  690 s → 0.19 h     面板显示 0.2h
dur_rem   =    0 s → 0.00 h     面板显示 0.0h
```

所以它**不会自愈**，要等当晚真正入睡才被清零。

### 修法（方案 B：结构快照）

- 合格 bout 结算时写 `s.sleep_last_struct`（秒 + hours/quality/end_t），午睡分支不写。
- `_sleep_view()` 的回落目标从 `dur_*` 改为该快照；连快照都没有才退回 `dur_*`。
- `_restore()` 回填：旧存档没有快照时，用 `sleep_bouts[-1]` 反推，部署重载后立刻正确。

结果：结构行恒等于「最近一次合格睡眠」，午睡再也进不来，且不丢上一夜的结构。

### 未修的关联缺陷（已知，别当成新问题）

`_night_key()` 用 `self.clock_offset` 换算，而 `clock_offset` 是**可变**的
（`sync_clock = true` 时每次同步重写）。进程重启/停机期间 `s.t` 冻结、墙钟前进，
偏移量跳变 → 已存的 `night.key` 与后来重算的 key 不再对应。
**现场**：服务器存档里 night `key=17` 跨度 `d17 00:13 → d18 09:51`（33.6h），
把两夜合成了一夜（`hours=16.11`、`bouts=2`、`cycles=5`），
而同一张卡的分期图只有 6.6 小时 —— 两处自相矛盾。

正确修法是让 `_night_key` 与 `clock_offset` 解耦（用 `t` 的稳定日序号），
或存档时把 key 连同当时的 offset 一起存。**本轮未动**，留作下一入口。

## 八、踩过的坑（重要，别重犯）

1. **`read` 默认只读 2000 行**。`plugin.py` 有 3200+ 行，按行号做手术时把文件截断过。
   对长文件做行级改写，必须显式 `limit` 或先 `fs.readFileSync` 拿全量。
2. **往类里插方法不能用 0 缩进**。顶格插入 `_last_night_view` 把 `LifeBodyPlugin` 提前结束，
   类里只剩 6 个方法（应 33 个），17 个 `@API` 全丢，服务器报
   `注册失败: WebUI 页面 now 引用了未注册的静态 API: webui_now@1`。
   **验证方法**：`ast.parse` 后数类内 `FunctionDef` 数量（`check_sleep_view.py` 门禁一已覆盖）。
3. **测试里改睡眠窗口很脆**。`_night_window()` 叠了三重抖动（入睡 ±36min、起床 ±40min、
   熬夜最多 +60min），写死时段可能反而覆盖当前钟点，人醒不过来。
   构造「中途醒来」请用 `_wake_up()` 或**拨 `clock_offset` 让钟点越窗**，
   不要把窗口设成 `(0,0)` —— 跨度为 0 会被当作 24h 记进 `sleep_night_window`，
   之后的午睡就不再被判成午睡了。
4. **`remote_ssh_exec` 不能传文件**，且多行 PowerShell 经 cmd.exe 会断。
   远端命令必须**单行**传输；部署文件用 `scp`（Windows 自带 OpenSSH）。
5. **`remote_ssh_cat` / `ls` / `grep` 在这台 Windows 主机上全部报错**（插件发的是 Linux 命令）。
   取远端文件内容用 `remote_ssh_exec` + PowerShell（`Get-Content`），并先设 UTF-8。
